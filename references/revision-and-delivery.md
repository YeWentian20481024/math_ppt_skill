# Revision, presentation choices, and delivery

## Recover the current revision

Read saved annotations and their highlighted content. Keep a mapping from stable content identity to action and revised location. Resolve an ambiguous page number against actual content; do not apply comments to a stale export. Check whether rebuild scripts use old snapshots before running them.

Separate requests to inspect, propose, and implement. A later implementation request can supersede an earlier review-only phase; neither creates unlimited permission to change unrelated scientific work.

## Choose layout for comprehension

Preserve an existing usable format and theme. Use restrained hierarchy and readable mathematical typography. Avoid an invented default institution or author. Do not require a fixed font size, slide count, aspect ratio, engine, or ban on overlays across all projects.

If overlays help reveal a derivation, distinguish logical frames from physical PDF pages. If navigation dots are requested, define what they represent. Validate actual link destinations, not only visible dots. For many frames, grouped section navigation can be more usable than tiny individual targets.

Keep citations attached to relevant claims and supply full references. The choice of footnotes versus end references is configurable. Never drop relevant sources to meet an arbitrary reference-page limit. Use original figures or properly attributed material that may be redistributed; do not assume an available PDF permits republication of all its contents.

## Notes and speaking route

Keep definitions, hypotheses, and essential experimental setup visible to the audience. Speaker notes carry pacing, transitions, expanded derivations, and anticipated questions. A request to hide presenter cues does not mean hiding scientific qualifications.

Prepare an optional shortened speaking route when duration warrants it. Record which content can be skipped without breaking later dependencies. Treat rehearsal time as an estimate until someone actually times it.

## Verify the delivered versions

After local changes, inspect changed pages and representative dense pages. After global style or order changes, inspect the whole rendered deck. Check formulas, clipping, chart labels, footers, citations, notes visibility, bookmarks, internal links, and the content/page map. Compiler warnings and screenshots test different things; neither substitutes for the other.

Keep the audience PDF, editable source, and companion script consistent. Report the actual checks and unresolved limitations rather than generic “all checks passed.” Do not overwrite annotated originals.

## Public release boundary

Prefer newly written examples using standard mathematics when research content is private. Never treat formula substitution alone as anonymization. Review source, generated text, metadata, speaker notes, annotations, embedded files, URLs, image metadata, and archive contents. Exclude build logs, editor backups, credentials, local preference records, and previous Git history.

A public release may carry the deliberately chosen public repository identity, but should not copy a local real name or email into commits without authorization. Inspect commit identity before publishing, or use an explicitly generic project identity for a fresh public package. Review a concrete release file list rather than uploading a whole working directory.
